# Development

Each directory in `platforms/` is an independent Gradle build. It includes the shared Java 17 project in `common/` and embeds its output in the platform JAR.

Common uses the platform compiler with `--release 17`, restricting bytecode and Java API use. It has no Minecraft or loader dependencies.

In IDEA, link the platform's `build.gradle` and use its required Gradle JVM. The root build runs each wrapper with the configured JDK. Set the corresponding `JAVA_HOME_<version>_X64` variables or use local Gradle toolchain discovery.

On Windows, run `.\gradlew.bat build` from the root. On Linux, run `bash ./gradlew build`. Release JARs are collected in `build/libs`. Root `clean` clears collected JARs and platform build outputs.

Capture build, data-generation and validation console output under the root project's `build/logs/`, never beside the root or platform wrapper. From the repository root in PowerShell:

```powershell
New-Item -ItemType Directory -Force build/logs | Out-Null
.\gradlew.bat check *> build/logs/check.log
$LASTEXITCODE
```

Use descriptive filenames for separate runs and inspect the actual Gradle exit code. Headless adapter tests use `src/adapterTest/resources/log4j2-test.xml` with a console-only appender; they do not create a platform-root `logs/` directory. Normal client/server runs retain their own logs inside the configured `run/` instance; opt-in disposable validation instances live under the platform's `build/`. Ignore rules prevent accidental commits but do not determine where a process writes its logs.

With Python 3.11+, run `python scripts/verify.py --project . --release` after a root build, or pass `--target <loader-version>` after a platform build. This checks packaging and metadata. Verify client world entry, dedicated-server readiness and actual mod behavior separately in disposable instances.

Run `runClient` or `runServer` through the matching platform wrapper. Development worlds and configurations live in that platform's `run/`. Review the Minecraft EULA before enabling a dedicated server instance.

`check` runs loader-free `coreTest` contracts and NeoForge `adapterTest` contracts. Adapter tests verify NBT round trips, offline ownership transfers, dirty-state propagation, JSON validation and command registration without starting a game. `python scripts/verify_combat_resources.py` validates weapon profiles and icon mappings.

Build previews load published textures from the runtime classpath; they do not require the ignored `art/` workspace. `StatusIconPreview` renders the thirteen current 32px status icons at native and nearest-neighbor preview scales. Missing, unreadable or incorrectly sized published images still fail the check. Historical 16px comparisons are optional: from the NeoForge module run `gradlew compareStatusIcons -PstatusIconSources=<original-icon-directory>`. This writes `build/ui-preview/status-icons-comparison.png` and requires all thirteen originals explicitly; it is not a dependency of build/check.

Run root `gradlew runData` to regenerate `common/src/generated/resources/`. `BuiltinMods` and `BuiltinCombat` are authoring defaults; base translations are in `common/src/datagen/resources/lang/`. Runtime loading uses the generated data-pack resources and permits overrides; it does not fall back to code defaults. Generated resources are embedded alongside static images, with `.cache/` excluded from the release. `python scripts/verify_mod_resources.py` checks definitions, models, standalone loot templates and unique texture paths across static/generated roots. Adapter contracts decode all generated definitions and validate 32×32 textures, binary alpha and visible content, retaining a white check for the default fallback. Never edit generated defaults as their source of truth.

Accepted subject art is published by Yagen-Pixel directly into `common/src/main/resources` from a reviewed publication manifest. `ModDataProvider` resolves each definition's explicit texture ID against `GatherDataEvent.getResourceManager(CLIENT_RESOURCES)` and emits a white placeholder only when absent. This manager loads `--existing` packs and excludes the generating mod, so old generated resources cannot suppress missing-image fallback generation. `ExistingFileHelper.exists` is unsuitable for this decision because disabled validation makes it return true unconditionally. Flame Feather B is the first static subject; its source, reference packs, publication manifest and receipt are under `art/textures/batches/flame-feather-study-02/`. Remove a superseded generated placeholder before a build to prevent duplicate resource inputs.

`ModDefinition` compiles each explicit stat/operation/basis entry at every rank. `ModCatalog` validates and precomputes immutable cards, quality metadata and deterministic Creative ordering. `ModDefinitions` prepares the complete server catalog before atomic publication and synchronization; the client holds a separate catalog. `Bonus.inputAddition` represents additive elemental coefficients relative to total attack damage, retaining a useful basis even when the existing component is zero. It contributes to the Addition stage before independent multipliers. Legacy `inputAddin` remains in the initial addition stage; absent fields decode as zero in old saves and shot snapshots. Creative ordering groups each definition's complete rank range within its quality. Identity never determines effect semantics or category membership.

`ModItemData` stores definition ID and rank on physical `yagens_attributes:mod` items; dynamic Rivens additionally carry `RIVEN_ROLL`. Deposits allocate ledger UUIDs; physical withdrawals remove one uninstalled owned instance. `ModTransactions` validates the current catalog, Endo balance, permissions and resulting installed capacity before upgrading, then debits Endo on the same server thread. Schema 7 stores definition, optional Riven details, separate currency accounts and pending cycles, recompiles known cards when catalogs change and clears missing-definition bonuses without discarding ownership or installation. Schemas 1–6 migrate; existing Endo balances survive. Legacy custom cards retain their explicit modifiers and cannot masquerade as defined cards through metadata commands.

`ModModels` registers standalone models and resolves physical item variants from the component. The default model handles missing definitions/models. `ModTabIconMixin` overrides vanilla's cached Creative icon only for this Mod tab, rotating prebuilt level-zero stacks every 40 ticks. Model baking, icon rotation and actual player transfers/upgrades still require client/gameplay checks beyond headless contracts.

The NeoForge adapter owns Minecraft APIs, saved data, data components, mixins, networking and rendering. `WorldState.get(server)` resolves the authoritative overworld state. Its `ledger` marks saved data dirty on successful mutation; callers must remain on the server thread. `bonus(playerUUID, stat, Bonus)` changes player bonuses, and `visibility` changes privacy preferences. `ModLedger.Entry` and `Bonus` are immutable contracts. Source-indexed integrations can aggregate their modifier sources into a Bonus before publishing it.

`StatusProcEvent` fires after positive health loss or shield consumption. Repeated types represent independent procs; duration is the weapon's six-second baseline in ticks. `StatusContext` supplies immutable pre-defense status damage bases, including the hit's existing critical multiplier and volley share. `StatusEffects` implements the built-in layer engine. Extension handlers must use a distinct secondary path to avoid recursively resolving weapon modifiers or rolling new statuses.

The ranged-attribute mixin is mandatory. `scripts/verify.py` checks its descriptor registration, config bytes and accessor class in addition to common resources, bytecode and metadata. Rendering and networking still require in-game and remote-client validation; headless contracts do not establish gameplay parity.

Client tooltips use `ClientProfiles`, a cache committed only when a complete profile sync arrives. `OnDatapackSyncEvent` sends chunks of 64 definitions on login and reload; logout clears the cache. Protocol 22 uses up to 18 grouped warehouse cards, 8 compatible cards and 64 installed slot entries, with request IDs to discard delayed responses. Panel snapshots include the actual held ItemStack, progress, used capacity, the current player’s Endo balance and available Endo inventory space. `PanelService` validates the sender's weapon identity, category, slot occupancy and capacity on the server thread. It limits requests to 20 per player per second. Search is debounced; clients time out unanswered requests and can retry through Refresh.

`WeaponInspectionService` reads only a matching slot in the sender's currently open server menu, with item ID and weapon UUID guards. It does not assign identities or mutate inspected items. Requests are limited to one per two ticks; client caches hold at most 256 entries and refresh after 20 ticks. Reload/logout clear them. `WeaponProgress` is loader-free and canonicalizes level-local XP. `WeaponExperienceEvents` deduplicates held weapon identities, uses the shared conserving allocation algorithm and sends tiny progress updates instead of rewriting item components for every XP gain. Progress is stored centrally by weapon UUID in schema 7.

`ModInfo.Category` defines an explicit parent tree. `ModInventory` filters, groups exact variants, counts real copies and orders the complete result before pagination. Rarity, polarity and capacity cost are explicit metadata. `WorldState` migrates schemas 1–6, preserves prior installations and marks migrated data dirty. Both commands and panel handlers call the capacity-aware ledger operation with server-derived level/Creative state; lower-level ledger overloads without a player context remain available for trusted restoration/integration code.

`PanelGeometry` caches immutable layout rectangles in a 1100×600 logical canvas. `ModPanelScreen` transforms both drawing and pointer input into that canvas. `PanelPainter` is shared between the production Minecraft canvas and `ArsenalPreview`'s offscreen AWT canvas; adapter checks generate five design-fixture PNGs in `build/ui-preview/`, including a drag target and floating icon. They validate visual layout without claiming a running-game pass. No Warframe screenshot pixels are bundled. Existing status textures are 32×32; the authoring sources, prompt constraints and reproducible export procedure live in `art/status_icons/`. `StatusIconPreview` renders the original/retouched comparison alongside the panel and withdrawal fixtures.

`ModGesture` owns double-click identity/timing and drag/drop intent independently of Minecraft. The screen resolves geometry and presents icons/feedback; `PanelService` repeats all authorization against the held weapon and current ledger. `MOVE` atomically publishes a move or swap through `ModLedger.move`, checking both installed entries' permissions while preserving ownership and capacity. Removing another owner's shared entry uses `TAKE`; removing an owned entry uses `UNINSTALL`. Physical withdrawal is a distinct drop target for unoccupied owned definitions. Gestures are canceled by replies, modals, screen changes and Escape; background refresh waits until the pointer transaction ends. Protocol 13 includes independent status-marker snapshots and needs matching clients and servers.

`ModText` supplies applicability and rank/polarity/capacity metadata, with quality conveyed by name/modifier colors rather than a label. Maximum defined rank uses #55FFFF for rank text alone. Source bucket names and redundant copy/availability lines are omitted; ledger counts still support grouping, sorting and card badges. `StatText.bonuses` supplies value-first lines with chance percentage units and duration seconds. Elemental input-relative coefficients retain their declared basis. Panel permission/bound-weapon/owner details require Shift; the formatted detail cache includes that expansion state. `PanelPainter.Card` keeps rank/category separate so color applies to rank independently, and draws centered names without a title backplate.

`WeaponEligibility` centralizes nonstackable-single-item/profile checks for server identities and client hotbar filtering. `HotbarWeapons` uses the synchronized profile catalog and preserves slots 0–8 in relative order. Clicking sends native carried-item selection before REFRESH on the same connection; the screen discards the previous snapshot and gesture/selection state while waiting. External selected-slot changes trigger the same refresh boundary. No custom packet schema or inventory movement is introduced. Native selection is exercised in the disposable server with a socket-free ServerGamePacketListenerImpl because FakePlayer's listener deliberately ignores selection packets. Real client input/rendering and network ordering still need a connected-client check.

`PolarityGlyphs` defines stable E100–E108 font codepoints. `PolarityTextures` reads `art/polarity/*.png` during runData, preserves alpha silhouettes, normalizes runtime RGB to white, and exports nine 32×32 glyphs with aspect ratio and padding retained. Reference originals retain their native pixels, dimensions and source attribution in `art/polarity/Sources.md`. The Gradle data run passes the authoring path explicitly. Runtime and offscreen previews consume the generated PNGs, never the old approximate stroke geometry. A dedicated bitmap font and additive default-font reference preserve vanilla providers; custom JSON symbol strings retain the normal font.

`StatusMarkerSync` derives counts from authoritative layers, coalesces changes per entity until ServerTick.Post, and sends immutable full snapshots to trackers and the affected player. Start/stop tracking supplies replay/clear messages. The transient baseline and dirty set are not saved; server stop clears strong references. Procs and markers use independent layer state; neither creates or reads potion projections. `StatusMarkers` validates entity ID plus UUID, bounds its cache, clears on world changes, and caches formatted rows. `StatusMarkerLayout` grows rows upward from a fixed bottom anchor at height×(1+gap), using the configured columns and existing damage-icon font. Rendering respects depth, invisibility, camera mode, GUI visibility and range. `MarkerContracts` covers packet bounds, duplicate rejection, ordering, fixed-bottom geometry and generated glyphs; `MarkerPreview` is a design fixture rather than evidence of actual client rendering.

`DamageNumberTransform` produces camera-relative billboard geometry. At `AFTER_PARTICLES`, the renderer's global model-view stack already contains the view rotation; multiplying the event's view matrix into each label would apply that rotation twice. `PanelContracts` tests transforms, caches, inspection/progress/request/damage/profile/Mod-summary wire formats and stale-weapon rejection. The complete panel packet uses Minecraft's registry-aware Component and ItemStack codecs and requires a loader/game session for end-to-end verification. Display ordering is separate from enum ordinals so damage glyph IDs and proc masks remain stable.

`WeaponProfiles` prepares exact profiles and family defaults together, resolves registry items on reload and atomically publishes both item-identity and resource-ID maps. Combat lookup is O(1). `WeaponFamilies` maps explicit vanilla Java classes to categories, with `ClassDefaults` caching nearest-superclass matches. Exact item profiles take precedence. Fallback panel baselines inspect native default-stack attack attributes once per reload; per-stack dynamic baselines and custom ranged models need explicit integration. Clients receive the resolved table through the existing chunked sync.

`EndoCurrency` validates integer input, rejects balance overflow and computes a complete withdrawal allocation before mutation. `WorldState` stores separate Endo and Kuva accounts as NBT longs in schema 7; schemas 1–3 start Endo at zero and schemas 1–6 start Kuva at zero without replacing existing data. `EndoItem` and `KuvaItem` deposit the held stack on the server, consuming actual items even in Creative. `EndoTransactions` examines only canonical stacks of the selected currency and empty main-inventory slots, then applies its preflight plan and commits the new balance on the server thread. Failed preflight has no inventory or balance side effects. Panel mutations share the existing request budget and request IDs; currency actions use the sender's account independently of the held weapon. A stat-resolution error cannot replace the successful result of a committed transaction.

The modal quantity input captures pointer and keyboard interaction, suppresses background query refresh, and blocks duplicate submissions while awaiting a reply. Server replies update both balance and available space; input filtering and disabled buttons supplement server validation. Cross-save crash atomicity between vanilla player inventory files and world SavedData is not guaranteed by Minecraft; transfers use the normal server-thread mutation/save lifecycle.

`ModItems.ENDO` registers a single `yagens_attributes:endo` item and inserts it into the independent Items Creative tab. Shared resources add its generated-item model, English/Chinese names and a 32×32 refined legacy Mod essence icon. The original 16px source is under `art/item/endo/`; the active artwork is Endo A from `art/textures/batches/resources-study-01/publication.pixelproject.json`. The legacy exporter writes previews only and cannot overwrite reviewed runtime art. No legacy essence block or mission-key Endo subsystem is imported. Defined Mods support rank growth and Endo upgrades through the shared server transaction; legacy custom cards have no inferred upgrade definition.

`RangedStats` owns the bounded multishot roll and per-use charge clock. `RangedUseEvents` processes only supported players' item-use events, with server-thread-local weak session maps. Client prediction lives in `ClientRangedUse`; its first tick requests the authoritative active rate after the vanilla use packet. Requests validate held item/weapon identity and are bounded to 20 per second. Replies carry a per-use sequence and cannot update a later charge. Clock corrections rebase only this feature's accumulated advancement and preserve duration edits from other event handlers.

`ProjectileWeaponItemMixin` replaces native count generation with one template round and routes a supported shot through the native projectile factory/aim methods once. `RangedShooting` serializes native projectile state once when copies are needed, removes the entity UUID/passengers, constructs fresh instances, restores exact motion and stamps a shared immutable `ShotData` snapshot. It does not intercept world-wide entity joins or keep a pending-next-arrow table. Spawn failures renormalize the damage factor to surviving entities; virtual projectiles cannot duplicate ammo or thrown weapons. `ShotData` serializes through a server-side NeoForge attachment and records numeric modifier sources, without Mod ownership/instance records. Weapon items additionally retain intrinsic polarity, XP-absorption and catalyst components.

`TridentItemMixin` routes the explicit native throw spawn; `CrossbowItemMixin` and the bow loose event prevent zero-multishot shots from spending ammo. `VirtualArrowMixin` and `VirtualTridentMixin` protect both normal pickup and Loyalty return/drop paths. `RangedCooldownMixin` uses the platform-provided MixinExtras field wrappers on `LivingEntity.hurt`: ranged reads of `invulnerableTime` return zero, and ranged writes to that field and `lastHurt` are suppressed. No damage-type tags are changed globally, and no target field is temporarily zeroed during callbacks. `RangedContracts` checks the exact mapped methods, field owners/access counts and native invocation descriptors against the target bytecode; this is not evidence that the mixin transformer or gameplay ran successfully.

Porting requires new adapters for launch hooks, charge synchronization, projectile attachment serialization and cooldown access in addition to the existing event adapter. `common/` remains Java 17 and loader-free. Verify actual release-JAR startup, remote-client prediction, ammo/repair accounting, Infinity, Quick Charge, tipped/spectral arrows, fireworks, piercing, Loyalty, owner death and competing damage mods in game separately.


`ShieldRules` separates ordinary damage, unarmored shield input and health-only input. `DefenseEvents` applies live Viral/Magnetic multipliers after weapon calculation, then encodes shield expenditure plus health loss into the NeoForge damage container and limits its absorption reduction. Shield overflow retains the original hit's proportional native armor mitigation; custom defense pipelines need an explicit adapter. `ShieldAbsorptionMixin` supplies a positive natural shield capacity without permanent attribute modifiers, caps external additions and commits an eligible gate before absorption reaches zero and reactive damage callbacks run. `AbsorptionEffectMixin` adds repeatable absorption-effect grants only for positive natural shield capacity. `ShieldState` saves recharge delay, fractional recovery, eligibility, the current recorded amount and gate time. External gains never arm a spent gate. Attributes apply to all registered living entity types; default natural capacity is zero.

`StatusState` stores source UUIDs and independent layer clocks in an entity attachment. `StatusEffects` derives transient attribute modifiers, batches due pulses and reuses each AoE query across layers/owners. Procs do not register or create MobEffects, consult potion applicability, or react to vanilla effect removal. Milk and `/effect` cannot apply or cure these layers. Head markers use their own payloads and tracking snapshots. Rejoining entities restore transient modifiers from saved layers. `StatusControlMixin` pauses active Mob AI while controlled, including Brain-based mobs, without mutating NoAI or suspending physical/living updates. Confusion supplies an explicit goal-selected target and registered Brain attack memory; specialized AI may need its own adapter.

### Status integration API

NeoForge integrations use `yagen.waitmydawn.yagens_attributes.api.StatusApi` on the logical server thread. `DamageType` remains in the loader-free common core. Compile against the matching platform artifact; optional integrations must isolate API references in an adapter that loads only when the mod is present. No published Maven coordinate is assumed.

- `count(entity, type)`, `durationTicks(entity, type)`, `isFrozen(entity)` and `isControlled(entity)` query authoritative gameplay state. Duration is the maximum remaining layer clock, which pauses for Cold during a full freeze.
- `layers(entity)` returns a detached, immutable list containing type, source UUID, resolved damage base, remaining lifetime, next pulse, age and critical tier. It never exposes the mutable attachment. Client head-marker counts are a separate presentation snapshot and do not contain full layer data.
- `apply(entity, type, ownerUuid, damageBase, weaponDurationTicks[, criticalTier])` attempts one proc and returns whether a layer was accepted. The damage base already includes offensive bonuses, critical scaling and volley share; the engine applies the type's pulse coefficient and live target defenses. Weapon duration must be 1..72000 ticks; type-specific duration scaling still applies. Critical tier is 0..100 and affects number presentation only. Electricity and Gas include an immediate pulse.
- `clear(entity, type)` and `clearAll(entity)` remove layers, residual armor/movement modifiers and control timers, stop active confusion targeting, and schedule a head-marker update. They return whether state was cleared.

Applications retain `status_immune`, `control_immune` and `immune_to/<type>` entity-type tags, stack limits and normal damage protections. Potion immunity alone does not block procs. Integrations should not mutate `StatusState` directly. Saved attachment fields remain stable. Icons live under `textures/status/`; the generated `damage_icons` font, authoring exporter and offscreen previews use that path. The former `*_status` MobEffect registry entries are removed, while same-named DamageTypes remain registered for secondary damage.

`StatusDamage` carries typed secondary damage with no live weapon item. It preserves ownership across dimensions for online players, leaves no strong attacker reference in persistent layers, never re-enters weapon resolution and does not trigger random statuses. Material and defensive state are read at each pulse. Independent layers share a native hit event per type/owner/weapon/pulse; `StatusArmorMixin` uses one calculation in linear mode and separate nonlinear layer calculations in none/improved_vanilla. Heat instead uses the combined pulse. Initial Electricity/Gas pulses are immediate; the saved clock then advances once per second. A dead Gas host transfers remaining layers to a native AreaEffectCloud with no potion effects. Blast death/stack detonations are queued with a 128-job per-tick budget and cleared at server stop. Their attacks can trigger native deaths and existing Blast layers but cannot recursively create random procs.

`ShieldPayload` synchronizes the local protection indicator; vanilla synchronization supplies absorption and attributes. `ShieldHeartMixin` wraps only the absorption-heart call and appends one lock to actual health hearts. It bounds large absorption displays before vanilla calculates heart rows. `ShieldPainter` is shared by the production overlay and `ShieldPreview`; `build/ui-preview/shields.png` is a design fixture, not a game screenshot. `StatusVisualPayload` sends sparse bounded feedback; local visuals obey their own client toggle, range and particle budget. Dedicated-server loading must not link these client implementations. All runtime JSONs and mixin registrations are checked by the release/resource verifiers; mapped-target ASM tests do not establish actual transformer application or gameplay correctness.

Secondary damage types are explicitly cataloged by resource key, so integrations using those registered types inherit secondary/cooldown/toxin semantics without a name-pattern guess. Shared damage-type tags suppress secondary knockback and classify Heat/Blast for vanilla fire/blast protection. Saved layers retain the original critical tier; mixed batches use the highest tier for number color only, without changing their already resolved damage.


Shield color preferences are client-only: `restoreNormalShieldColor` and `restoreOvershieldColor` default false and fall back to the original absorption-heart call independently. `showShieldGateLock` defaults true and affects only lock rendering, including when both colors are restored. The legacy `shieldHearts` key is retained as a custom-color master switch; it no longer controls lock rendering. Large shield numbers use the same color selection as hearts. No protocol, server-side protection or texture changes are required.


`ArmorRules.remaining` implements `K/(K+A) × L/(L+T)` using stable ratios; defaults are K=15 and L=8. `improvedRemaining` implements the legacy damage-dependent curve using retained damage directly, avoiding cancellation at high armor. `armorMode` selects none/improved_vanilla/linear, default linear; only linear reads `linearArmorScale` and `linearToughnessScale`. The previous fixedArmor/armorScale/armorToughnessScale keys are superseded without implicit value migration.

`ArmorFormulaMixin` injects at the CombatRules armor entry point with priority 2000. None returns without canceling; custom modes retain callers' durability and bypass behavior. Native armor-effectiveness enchantment changes are applied as a delta so an unchanged float reduction cannot erase the small remaining fraction at very high armor. Priority alone does not resolve competing cancellations, overwrites or return modifiers; test an explicit compatibility adapter where another mod replaces this calculation. Mixin application and injection ordering are distinct contracts; see the [Mixin priority API](https://github.com/SpongePowered/Mixin/blob/master/src/main/java/org/spongepowered/asm/mixin/Mixin.java).

`ArmorPenetrationEvent` exposes the target and DamageSource once per custom armor evaluation. Contributions accumulate independent armor/toughness percentage and flat penetration, then resolve `max(0, value × (1-percent) - flat)` before the curve and native enchantment delta. The target's attributes are never mutated. None does not publish this event. Future player attributes can contribute through a handler; launch-time projectile adapters must explicitly capture their penetration inputs rather than reading mutable equipment at impact. Independent DOT layers may cause multiple evaluations in nonlinear modes, so handlers must not consume one-use state merely because the event fires.

`CombatEvents.incoming` resolves offensive bonuses before native defense and captures `Combat.statusBases` directly. Prepared hits are keyed by DamageContainer identity and promoted in Pre only when the same container reaches actual damage processing. Post consumes the matching hit before secondary callbacks, and unfinished state is cleared at the end of a server tick. This separates attacks rejected by cooldown/blocking even when they reuse a DamageSource. `DefenseEvents` reconstructs the armor-free shield input from that container's reductions without rerunning offense.

For opt-in runtime checks, from `platforms/neoforge-1.21.1` run `gradlew --no-configuration-cache --init-script ../../scripts/combat-runtime.init.gradle runServer`. The init script creates `build/combat-validation`, binds loopback/port 0 and includes adapterTest only for that run. The test subscriber uses a NeoForge FakePlayer, writes `combat-runtime-report.json` with its process ID and native armor-set data, and requests clean shutdown on pass or failure. Inspect the report's `passed` field as well as the Gradle result. EULA/development-server requirements remain those of the normal runServer task. No test subscriber or test-only source set is included in the release JAR.

Omni is appended to the polarity enum to preserve existing ordinals and glyph codepoints. Its stable JSON key is omni, with codepoint E108. Polarity.matches centralizes asymmetric slot matching, including the Umbra exception; the screen and authoritative transactions use it for matching and capacity discounts. Protocol 22 rejects older peers before the expanded catalog reaches their enum decoder.

## Polarization and material items

`WeaponPolarityData` is the immutable persistent/network component `yagens_attributes:weapon_polarities`. It stores sorted unique slot-index/polarity overrides on the actual ItemStack. Unmodified slots keep data-pack defaults; resolution also retains occupied or overridden slots after a template shrinks. WorldState does not store polarities. Level/experience remain indexed by weapon UUID under the existing progress contract. Cloned item identities still require an explicit external migration/identity contract.

`PolarityRules` supplies rounded ordinary-slot drain, projected swap cost and the three standard Forma choices. All player-facing ledger install/move/upgrade paths receive slots resolved from the actual weapon. Trusted no-context ledger overloads preserve neutral-slot behavior for restoration/integration callers. Moves cannot worsen an existing over-capacity loadout unless Creative bypasses capacity. Installed-card badges show the actual drain in green for a discount and red for a penalty.

`ModTransactions.polarize` validates the held UUID, operable item, distinct supported target polarity and every installed Mod permission before mutation. Survival additionally requires rank 30 and inventory Forma, returns Mods to their original accounts, resets progress and consumes one Forma on the same server thread. Creative needs neither max rank nor Forma, writes only the slot component and retains rank, experience and installed Mods. Permissions remain authoritative in both modes. Ordinary XP stays `7+2L` after every reset. `ModTransactions.upgrade` requires holding an installed Mod's weapon so capacity uses its actual component. Creative skips Endo balance requirements and debits, including at zero balance; the panel displays the effective zero cost. Maximum ranks and ownership/shared permissions still apply. No polarization counter or XP penalty exists.

`ModItems.FORMA` and `KUVA` use Rare and Epic vanilla rarity respectively, 64-item stacks and the independent Items Creative tab. Their existing reviewed 32px textures remain static; models and descriptions are generated. Offhand Kuva clears the main-hand item's prior work penalty on right-click; it has no recipe. The critical-damage definition keeps its stable `nameless_glove` ID and changes only its translated display name to Organ Shatter / 肢解.

The weapon panel's Forma icon toggles slot-target mode, followed by a three-glyph selection and explicit cost/reset confirmation. P, arrows, Tab, Enter and Escape provide keyboard paths. PanelRequest carries the explicit polarity enum; requests retain sender/held-item checks and the existing per-player budget. Real client rendering/input has not been exercised. `PolarityTests`, `PolarityContracts` and the disposable runtime checks cover drain rounding, swaps, permissions, item NBT, packet validation, actual material consumption and repeat resets.

`ModDataProvider` also generates `assets/minecraft/atlases/blocks.json` from each bundled Mod definition's explicit texture ID plus the fallback. Native item models use the blocks atlas, while the vanilla directory sources omit arbitrary folders such as status. Explicit `minecraft:single` sources ensure the same PNG can serve GUI blits, bitmap fonts and baked item sprites. Minecraft merges atlas source lists across resource packs; the generated file adds sources without replacing vanilla ones. Catalog/model/atlas coverage checks prevent a valid PNG path from silently becoming an unstitched missing sprite. The seven damage Mods retain their status paths and no duplicate item PNGs are introduced.

Creative free polarization is also available through `/ya polarize` on a fresh operable weapon: the command allocates its identity before the common guarded transaction. Packet-based actions still require the existing matching held UUID. The disposable server exercises zero-rank fresh-item command use, low-rank progress retention, installed ownership/slots, zero and positive Endo balances, max-rank upgrade rejection and Survival debits.

## Built-in definitions and melee combo

`core/mods/` contains one `BuiltinMod` subclass for each of the 24 bundled definitions. The facade registers class instances and common quality/polarity metadata; no translated display strings or mutable translation table participate. `ModEffects` describes reusable additive, flat, elemental and per-combo entries. All UI translations are authored in `common/src/datagen/resources/lang/`; runData copies these inputs without bilingual overlays. Developer-facing numeric descriptions remain English JSON editing guidance.

`Combo` owns loader-free thresholds, absolute expiry, duration and conditional chance-zone conversion. `ComboService` stores bounded, nonserialized player attachments keyed by weapon UUID. A main-hand direct melee snapshot receives the pre-hit chain tier; successful Post damage credits the snapshot identity. Status damage and projectile attacks do not credit or consume it. Positive shield blocks credit the defending wielder when holding a melee weapon. The main-world game clock continues while a weapon is holstered and is stable across dimension clocks; death/logout do not persist chains. Client packets carry rules and remaining/duration ticks, so local HUD countdown needs no per-tick server packet.

`MeleeAttributes` translates attack-speed factors and flat entity reach into unique transient vanilla modifiers, without touching item components, attack_damage or block reach. It updates only changed modifier values, removes them when equipment no longer qualifies and rejects non-finite custom results without interrupting player ticking. Panel and inspection services resolve the same combo chance additions. `ComboHud` draws only the local chain, obeys hide-GUI and the configurable visibility/offset/scale controls, and clears on logout.

The second batch adds four legacy-style 60/60 elemental Mods, Body Count, Blood Rush, Weeping Wounds, Drifting Contact, Fury and Reach. ## Experience-point purchases and Kuva

`ExperiencePoints` defines vanilla cumulative XP and fixed purchase prices independently of the loader. Anvil prices use T(n); enchanting uses T(offer)-T(max(0,offer-tier)), retaining the offered-level prerequisite and lapis cost. Balances derive from actual level/progress because vanilla level debits can leave totalExperience stale. Overflow and invalid state fail affordability checks. Remaining XP is inverted by binary search; the native float progress field remains the precision boundary.

`ExperiencePayments` writes the resulting level/progress and bounded totalExperience, using ServerPlayer's setter to invalidate XP synchronization. Purchase debits do not fire earned-XP hooks, which can redirect awards into weapon progress. `AnvilExperienceMixin` replaces affordability and debit while suppressing only the final expensive-result rejection; the earlier creative applicability check is preserved. The vanilla rename cap, result computation, material cost and anvil break event remain. `EnchantmentExperienceMixin` wraps the successful offer's callback inside its native synchronous lambda, paying once before invoking the original callback with zero level debit so seed renewal remains native. Client mixins replace cost text with points and remove the anvil warning; they do not change enchantment generation or prerequisites. Custom XP curves or menu overrides require an explicit adapter.

`KuvaInteractions` accepts only a qualifying main-hand event with offhand Kuva and positive effective REPAIR_COST. Its item/block/entity entry points use the same server transaction. Success sets that component to zero, consumes one Kuva outside Creative, synchronizes the inventory, and stops ordinary item use. No other components are replaced. Client handling acknowledges the action without mutating stacks; spectator, wrong-hand and no-penalty attempts pass through. Material descriptions are translation-key lists, including Kuva's usage hint.

## Kuva cycling and storage gestures

`RivenService.cycle` verifies ownership or installed sharing permission, the actual held weapon for installed cards, current rules, available Kuva and absence of an existing pending choice. It preserves weapon binding, category, rank and polarity, samples a new layout/qualities, then commits the candidate, incremented current count and debit on the server thread. The first cycle costs one Kuva, increasing to a permanent cap of sixteen. Creative uses the same fee. Choosing old still counts; choosing new recompiles against current disposition before replacing bonuses. Pending candidates persist by Mod UUID in schema 7, so closing the screen or restarting does not resample or refund them. Upgrade, physical withdrawal and drop reject unresolved candidates. A candidate invalidated by a rules reload can still be discarded by keeping the current card.

`ModPanelScreen` treats the weapon-footer Kuva icon and storage balance as cycle drop targets before ordinary slot gesture resolution; the gesture does not relocate the Riven. Selection plus clicking the weapon icon provides an equivalent path. The modal displays current/candidate cards, supports pointer selection and arrow/Enter/Escape controls, and disables submissions while awaiting the authoritative reply. Pending data survives closing the modal. The stored Kuva quantity is visible only for a positive balance or a Riven in the account, current installations or physical inventory, including veiled Rivens.

Storage right-click withdraws one uninstalled owned card using the existing inventory-space transaction. The native drop key targets the hovered card, with Ctrl selecting at most 64 copies. `ModTransactions.drop` groups exact metadata and bonuses, requires the requested UUID to remain present, excludes occupied/foreign/pending entries, and restores ledger entries if native world insertion rejects the ItemEntity. It never uninstalls a card implicitly. Search input captures typing before the drop-key handler.

`StatText.bonuses` partitions formatted entries by numeric sign and appends all negatives after positives. Independent multiplication carries its numeric sign separately in the wire summary, avoiding interpretation of localized display strings. `ModText.rank` adds a cycle glyph only for a positive count. The RESET source and provenance are `art/ui/cycle.png` and `cycle-source.json`; `PolarityTextures.glyph` exports its alpha silhouette to 32px, while runData generates `font/mod_symbols.json` and its default-font reference.

`ModText.properties` is the shared property list for physical tooltips, card details and cycle comparison. Riven names already identify their exact target, so the list omits the scope row for Rivens. Detail layout derives its single-line count from that list rather than assuming a fixed metadata prefix. `PanelCanvas.centeredComponent` measures the displayed styled sequence, preserving cycle/polarity fonts and rank/rarity colors. Modal surfaces render above EditBox's elevated text plane to prevent background search text from leaking into comparison cards.

## Riven rules preview

`RivenPool` resolves a sorted eligible trait list once for a weapon profile. It assigns one bit per distinct stat, so multiple trait IDs with the same stat retain their individual draw weights but share the exclusion/reservation identity. The 64-trait catalog limit bounds the representation. Positive/negative stat masks implement the same remaining-slot feasibility rule as the previous set-based sampler. `RivenRules.rollWeapon` consumes this pool without changing random-call order or sorted selection order; `RivenAnalysisTests` compares sampled lines against the previous implementation using deterministic seeds.

`RivenAnalysis` computes inclusion probabilities conditional on a layout. Each positive transition contributes its path probability to the chosen trait, then merges states with the same used-stat mask. Negative selection expands the resulting states once. The result preserves alias weights, one-negative reservation, sign eligibility, category applicability and strict physical thresholds. It does not divide blindly by pool size or use a sampled frequency estimate. Impossible layouts are reported without renormalizing the layout-selection probability. Endpoint values share `RivenRules.value` with actual definition compilation and apply the opened card's rank; negative intervals are reordered numerically.

`RivenRulesScreen` reads the synchronized catalog and exact bound-item profile. Its four-analysis cache is scoped to the screen and invalidated when either immutable snapshot changes. It computes on layout/data changes, not during rendering or combat. Native layout/back buttons support focus and narration; the list supports a draggable scrollbar, wheel and paging keys. Selecting a layout is read-only and cannot constrain a paid cycle. The cycle screen's `?`/F1 entry is disabled while a request is pending. Returning reuses the parent screen and requests an authoritative cycle refresh, preserving selection and pending results. No packet or save schema change is needed. Real client rendering/input has not been exercised.

## Composable warehouse filters

`ModFilter` is an immutable conjunction of disjunctions over explicit rarity, reservation and rank metadata.
